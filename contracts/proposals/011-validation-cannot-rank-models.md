# 011. 지금의 validation 점수로는 model을 고를 수 없다

## 무엇이 관측됐나

Kaggle에 올린 두 실행의 순위가 로컬과 반대로 나왔다.

| | `…lr3e4-s42-c632` | `…lr2e4-s42-f7a5` |
| --- | --- | --- |
| 로컬 mAP@[0.75:0.95] | 0.9518 | **0.9572** |
| 로컬 TP / FP (IoU 0.5) | 2170 / 33 | 2171 / 34 |
| **Kaggle** | **0.46354** | 0.44651 |

두 제출 CSV를 상자 단위로 맞춰 보면 **3,229개 예측의 class가 100% 일치**한다. 위치도
서로 IoU 중앙값 0.982로 같다. 차이는 변 좌표 1.2 px(중앙값)와, 한쪽이 더 낸 score 0.39
이하짜리 상자 20개뿐이다.

로컬에서 앞섰다는 그 차이의 실체는 **TP 한 개**다(2,200개 중). 측정값이 아니라 잡음이다.

## 원인: validation이 train과 구분되지 않는다

`scripts/validation_similarity.py`로 `v4-seed42-8020-group` 전수를 쟀다.

```
python scripts/validation_similarity.py --dataset v4-seed42-8020-group
```

validation crop마다 **같은 class의 가장 비슷한 train crop까지의 평균 픽셀 차이**(0~255
척도)를 잰 결과다.

```
train crop 8,833 | validation crop 2,200
  픽셀이 완전히 같은 crop : 0개 (0.0%)
  거리 < 1  : 32.1%      중앙값 1.43
  거리 < 3  : 79.3%      p90    4.64
  거리 < 5  : 91.2%
  거리 < 10 : 97.3%
  다른 class 대조군 중앙값 : 27.28
```

**복사·재사용은 없다.** train crop 8,833개 중 8,815개가 서로 다르다. 그런데도
validation crop의 79%가 train에 픽셀차 3 미만짜리 짝을 가진다. 3이면 사람 눈으로
구분되지 않는다. 다른 class 대조군이 27.28인 것과 비교하면 같은 class끼리는 사실상
같은 그림이다.

이유는 데이터의 성질이다. 촬영 조건이 `_0_2_0_2_{70,75,90}_000_200` 세 가지뿐이고
(v3·v4 모두 99.7%), 조명과 배경이 고정이다. 알약 하나가 가질 수 있는 겉모습이 사실상
각도 3종뿐이다.

## 이것은 split 결함이 아니다

`v4-seed42-8020-group`의 split 자체는 규칙대로 동작했다. 확인한 내용이다.

- train/validation 양쪽에 걸친 group **0개** (837 + 207 = 1044)
- `split.train_only_categories` 비어 있음, 57개 class 전부 양쪽에 존재
- group 하나 = 알약 조합 하나 = 각도 3장, 통째로 한쪽에만 감

**data pipeline에 고칠 것이 있다는 뜻이 아니다.** 조합 단위로 아무리 잘 갈라도 같은
알약의 겉모습이 양쪽에 나타나는 것은 막을 수 없다. 그러므로 **재분할로는 해결되지
않는다.** group 규칙을 더 조이자는 제안이 아니다.

## 요청

### data에게 — `dataset_summary`에 유사도를 남겨 주기를 바란다

지금은 이 값을 알려면 사람이 따로 재야 한다. 전처리가 끝난 자리에서 한 번 재어
`dataset_summary.json`에 남기면, 그 dataset으로 학습한 모든 실행이 "이 검증 점수를
믿어도 되는가"를 함께 들고 다니게 된다.

```
split.validation_similarity: {
  "median_distance": 1.43,
  "near_duplicate_ratio_3": 0.793,
  "measured_crops": 2200
}
```

- 전수 측정은 이미지를 전부 디코딩해야 해서 전처리 시간이 늘어난다. **선택 설정으로
  기본값 꺼짐**이면 기존 동작이 그대로 유지된다.
- 새 key만 더하는 것이므로 `schema_version`을 올리면 되고, 읽는 쪽은 없어도 동작한다.
- 계산 방법은 `scripts/validation_similarity.py`에 있다. import하지 말고 필요한 만큼
  옮겨 쓰기를 권한다. `scripts/`는 pipeline의 계약이 아니다.

### evaluate에게 — 채점되지 않는 class를 validation mAP에서 뺄 수 있게 해 주기를 바란다

`competition-plus-other` 산출물의 57번째 class `기타 알약`(`999999`)은 제출 CSV에서
빠진다(`006`). 그런데 로컬 mAP는 이 class를 포함해 57개로 평균을 낸다. 즉 **로컬과
Kaggle이 서로 다른 class 집합을 평균**한다.

`006`이 `submission_excluded_category_ids`로 제출만 걸러 준 것과 같은 방식으로, 지표
쪽에도 선택 설정을 두기를 요청한다.

```
evaluate.metrics_excluded_category_ids: [999999]   # 기본값 []
```

- 기본값이 빈 목록이면 지금 동작과 같다.
- `006`이 "validation 경로에는 적용하지 말라"고 했던 것과 **모순되지 않는다.** 그때
  요청은 제출 CSV에 관한 것이었고, 이번은 지표를 Kaggle과 같은 집합으로 맞추자는
  것이다. 두 값을 모두 보고 싶을 수 있으니 기존 mAP를 지우지 말고 나란히 남기는 편이
  좋겠다.
- 이것만으로 0.95와 0.46의 격차가 메워지지는 않는다. AP 0.945짜리 class 하나를 빼는
  일이다. 비교 가능성을 위한 것이지 원인 해결이 아니다.

## 팀이 정해야 하는 것 — 무엇으로 model을 고를 것인가

위 두 가지는 계기판을 고치는 일이다. **어떤 실험이 더 나은지 판단할 근거는 여전히
없다.** 선택지는 이 정도이고, 정하는 것은 팀이다.

1. **Kaggle 점수만 쓴다.** 정확하지만 제출 횟수 제한에 걸린다.
2. **train 안에서 촬영 각도로 나눈다.** 예를 들어 `_90_`만 validation으로 뺀다. 각도가
   달라도 같은 알약이라 여전히 쉽지만, 지금보다는 낫다. 실제로 얼마나 나은지는 위
   도구로 재 보면 바로 나온다.
3. **더 큰 dataset을 쓴다.** `v3`는 10,495장이고 `v4`는 3,061장이다. 유사도 자체는
   비슷하겠지만 잡음은 줄어든다.

이 문서는 1·2·3 중 무엇을 하자는 제안이 아니다. **지금 숫자를 믿고 model을 고르는 것을
멈추자**는 제안이다.

## 이번 변경에서 한 것

`scripts/validation_similarity.py`와 그 test뿐이다. 어떤 pipeline도 수정하지 않았다.
표본으로 돌리면 비교 대상이 줄어 유사도가 실제보다 낮게 나오므로(v4를 250장으로 재면
37%, 전수는 79%), `--sample` 결과에는 "쓸 수 있다"는 판정을 내리지 않고 하한선이라고만
말한다.
